# قواعد واجهات برمجة التطبيقات (API Engineering Rules)

## 1. المعايير والتصميم
- الالتزام بمبادئ RESTful الصارمة أو عقود RPC/GraphQL الواضحة.
- استخدام رموز حالة HTTP القياسية بشكل صحيح:
  - `200 OK` للنجاح مع إرجاع بيانات.
  - `201 Created` عند إنشاء مورد جديد بنجاح.
  - `204 No Content` عند النجاح بدون محتوى راجع (مثل الحذف).
  - `400 Bad Request` عند فشل التحقق من المدخلات.
  - `401 Unauthorized` عند غياب أو بطلان المصادقة.
  - `403 Forbidden` عند غياب الصلاحية للوصول للمورد.
  - `404 Not Found` عند عدم العثور على المورد.
  - `409 Conflict` عند حدوث تعارض في حالة المورد.
  - `422 Unprocessable Entity` لأخطاء منطق الأعمال.
  - `429 Too Many Requests` عند تجاوز معدل الطلبات المسموح به.
  - `500 Internal Server Error` للأخطاء غير المتوقعة (مع إخفاء التفاصيل عن العميل).

## 2. بنية الاستجابة الموحدة (Standard Response Envelope)
يجب أن تتبع كافة الاستجابات هيكلاً موحداً:

```json
{
  "success": true,
  "data": {},
  "meta": {
    "timestamp": "2026-10-02T10:00:00Z",
    "requestId": "req_123456"
  }
}
```

وفي حالة الخطأ:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "البيانات المدخلة غير صحيحة",
    "details": [
      { "field": "email", "issue": "صيغة البريد الإلكتروني غير صالحة" }
    ]
  },
  "meta": {
    "timestamp": "2026-10-02T10:00:00Z",
    "requestId": "req_123456"
  }
}
```

## 3. الأمان وتحديد المعدل (Security & Rate Limiting)
- تطبيق حدود زمنية ومعدلات استهلاك واضحة لكل مفتاح أو مستخدم أو عنوان IP.
- استخدام مفاتيح عدم التكرار (Idempotency Keys) لكافة عمليات الدفع وإنشاء الطلبات الحساسة.
